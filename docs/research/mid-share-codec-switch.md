# How cheaply can a live pair change codec mid-share?

Research for #128 (map #125, "Pick video codecs by what the streamer's machine can afford"). Written 2026-10-21 against the W3C WebRTC editor's draft (13 March 2025 snapshot with Candidate Additions), libwebrtc `main` (fetched 2026-10-21), chromestatus, Bugzilla, MDN's browser-compat-data, and a measurement run in Chrome for Testing 156.0.8078.4 and Firefox 155.0 (the builds Playwright 1.63 ships). Claims are cited inline. **Measured** marks something observed in that run, **Source-read** something read in libwebrtc source, **Inference** a conclusion drawn from those. Nothing is marked verified without a source or a run behind it.

## Answer in brief

- **The cheapest way is `sender.setParameters()` with `encodings[0].codec`, no renegotiation.** The browser keeps the same transport and SSRC, recreates the send stream with the new encoder, and sends one keyframe. The viewer sees no freeze: in a local run the longest gap between rendered frames was 67 to 100 ms against 51 to 83 ms before, with one extra keyframe decoded, no PLI, no freeze. The connection's bandwidth estimate did not move.
- **Support:** Chromium (and so Chrome and Edge) from 119, Firefox from 142, Safari not. The codec has to be one the pair has already negotiated; otherwise `setParameters` rejects with `InvalidModificationError`. Our pairs already negotiate every codec both sides share (ADR 2 trims only what the peer cannot decode), so AV1's fallbacks are all on offer.
- **The catch is the next negotiation.** In Chromium a codec chosen by `setParameters` is silently dropped, and the sender goes back to the first codec in the offer, when a later negotiation does not describe that codec parameter for parameter the way `getParameters().codecs` did (the cause is read from source; the revert itself was measured). Our screen seed (`x-google-start-bitrate`) is on the fmtp line of the first remote description only, which makes exactly that mismatch. **Measured:** with the seed, a plain re-offer returned the sender from VP9 to AV1. So the switch must also call `setCodecPreferences` with the new order on every video transceiver, so that whatever the next negotiation is, it lands on the same codec.
- **The fallback is `setCodecPreferences` plus an explicit offer** (what `src/lib/mesh.ts` already does at transceiver creation, applied again). It has the same viewer cost (one keyframe, same SSRC, no freeze, **measured** in both browsers) but costs a full offer/answer per pair, with perfect-negotiation glare to handle. It is the only way in Safari and the way to go when `setParameters` rejects.
- **The bandwidth seed is not touched by either path** unless a later description carries a *different* start bitrate. **Source-read:** libwebrtc restarts the estimate only when `x-google-start-bitrate` is present and differs from the last one. Our `#forSenders` already seeds only the first remote description, so a codec switch must not add one.
- **Our code needs care in four places:** `#prefer` runs only when a transceiver is created; the controller's window holds CPU-limited samples from before the switch; the telemetry window closes on the codec change by itself but as an ordinary `window` row with no reason; and a viewer who joins later must be offered the demoted order from the start.
- **How often it can happen:** each switch costs one keyframe and an encoder restart per video sender. The map's settled rule (leave AV1 on a sustained CPU limit, stay off it until the share ends) makes it a once-per-share event, which is affordable. Nine pairs mean nine independent encoders, so nine keyframes at about the same moment (see "Several pairs at once").

## What the two mechanisms are

### 1. `setCodecPreferences` then renegotiation (our current path)

`RTCRtpTransceiver.setCodecPreferences(codecs)` sets `[[PreferredCodecs]]`, which the next `createOffer`/`createAnswer` uses to order the m-section's codecs (PC, "setCodecPreferences" and the offer steps that apply `[[PreferredCodecs]]`). It does not by itself fire `negotiationneeded`: **measured** in Chromium 156, calling it on a live sender raised no `negotiationneeded` event. The offer has to be made on purpose (`pc.setLocalDescription()` in `#offer`). The sender then uses the first codec of the negotiated send list.

In libwebrtc a new remote description whose first codec differs makes `WebRtcVideoSendChannel::SetSenderParameters` set a new send codec, which calls `SetCodec`, which calls `RecreateWebRtcStream` (W: `media/engine/webrtc_video_engine.cc`, `SetSenderParameters` and `WebRtcVideoSendStream::SetCodec`; the source itself carries a TODO that this is a recreate, not a reconfigure, bugs.webrtc.org/8830). **Source-read.**

### 2. Per-encoding `codec` via `setParameters`, no renegotiation

- **Spec.** `RTCRtpEncodingParameters.codec` (type `RTCRtpCodec`): "Optional value selecting which codec is used for this encoding's RTP stream. If absent, the user agent can choose to use any codec negotiated for sending. When codec is set and [[SendCodecs]] have been negotiated, the user agent SHOULD use the first [[SendCodecs]] matching codec for sending, according to the codec dictionary match algorithm with ignoreLevels set to true." (PC, Candidate Addition 49, PR #2985.)
- **Validation.** `setParameters` rejects with `InvalidModificationError` when an encoding "contains a codec not found in choosableCodecs", where `choosableCodecs` is `parameters.codecs`, else `[[PreferredCodecs]]`, else the implemented send codecs. It rejects with `OperationError` "if the user agent does not support setting the codec for any encoding or mixing different codec values on the different encodings" (PC, setParameters validation steps). The motivating goal, from the extension PR: "make it possible to change codec without re-negotiating" (EXT-PR, merged 2023-04-20, moved to PC in August 2024).
- **Chromium.** Shipped in **M119** on desktop, Android and WebView, flag `RTCRtpEncodingParametersCodec` (CS; I2S). Edge mirrors Chrome (BCD). The Intent to Ship names the use case: "switching codecs on the fly", with AV1 for static slides as one example (I2S, Philipp Hancke's reply).
- **Firefox.** Bug 1894137 "Implement RTCRtpEncodingParameters.codec": RESOLVED FIXED, landed on mozilla-central 2025-06-26, Firefox **142** (BZ; BCD agrees: `firefox: 142`). The bug's test note says all WPT cases pass except the one for multiple codecs in a single simulcast stream, which does not matter to us (one encoding per sender).
- **Safari.** Not implemented: BCD says `safari: false`, and the WebKit standards position is only "support" (https://github.com/WebKit/standards-positions/issues/179, via CS). I found no WebKit release note that adds it (searched Safari Technology Preview notes up to STP 254). Treat Safari as unsupported; it stays on `setCodecPreferences` plus an offer. ADR 17 already makes Safari best-effort.
- **libwebrtc behaviour (what happens inside).** `SetRtpParameters` notices the changed `codec`, `ResolveSendCodecs` looks the codec up in the *negotiated* codecs (error `INVALID_MODIFICATION`, "Attempted to use an unsupported codec for layer", when it isn't there), and `ApplyChangedParams` sets the new send codec on the channel, which goes through the same `SetCodec`/`RecreateWebRtcStream` path as a renegotiated change. **Source-read** (W: `media/engine/webrtc_video_engine.cc`, `ResolveSendCodecs`, `SetRtpSendParameters`). The two mechanisms therefore reach the same encoder restart; the difference is the signalling and the stickiness, below.

## Measured: what the viewer sees

Setup: one local `RTCPeerConnection` pair in a page, a 1280x720 canvas capture at 30 fps (moving shapes) as the video track, `maxBitrate` 3 Mbps, AV1 first in `setCodecPreferences`, the screen seed `x-google-start-bitrate=2700` munged into the answer as `withStartBitrate` does, 6 s warm-up, then the switch to VP9 (and VP9 to AV1 once), then 6 s more. Receiver rendered-frame times from `requestVideoFrameCallback`, sender and receiver `getStats` polled every 250 ms (40 ms for the byte trace). Chrome for Testing 156.0.8078.4 and Firefox 155.0, headless, Linux, software encoders, no loss, no network shaping.

| | Chromium 156, `setParameters` | Chromium 156, preferences + offer | Firefox 155, `setParameters` | Firefox 155, preferences + offer |
|---|---|---|---|---|
| Renegotiation | none | yes (manual offer) | none | yes |
| SSRC | unchanged | unchanged | unchanged | unchanged |
| Extra keyframes decoded by the receiver | 1 (once 2) | 1 | 1 | 0 (count stayed at 1, not explained) |
| Receiver `freezeCount`, PLI | 0, 0 | 0, 0 | 0, 0 | 0, 0 |
| Longest gap between rendered frames after the switch (before it) | 83 to 100 ms (67 to 83) | 82 to 99 ms (52 to 83) | 101 ms (51) | 84 ms (51) |
| `availableOutgoingBitrate` across the switch | unchanged (5.4 to 6.4 Mbps depending on run) | unchanged, also when the seed was written into the new answer again | not exposed | not exposed |
| Sender bytes sent | continuous (no reset) | continuous | n/a | n/a |
| Receiver `inbound-rtp.codecId` | switches to the new codec | switches | switches | switches |

Reading it:

- **No visible gap.** The longest inter-frame gap stays within one or two frame intervals at 30 fps of what it was before. There is one extra keyframe on the receiver in both paths. Sender `keyFramesEncoded` is **not** a usable signal here: it stayed at 1 across the switch in Chromium while the receiver decoded a second keyframe.
- **Both mechanisms cost the viewer the same.** What differs is what the streamer pays: no offer, no answer, no glare handling with `setParameters`.
- **`framesEncoded` and `bytesSent` carry on** in Chromium, so `readSample`'s `sendBitrate` (a bytes delta) has no discontinuity at the switch. In Firefox the sender's `framesEncoded` barely advanced after the switch (125 to 126 in 6 s) while the receiver kept decoding about 21 frames a second; I took it for a stats quirk (the outbound entry may be a new one) and did not chase it. Our Firefox telemetry rows read the same counters, so a Firefox switch may leave one odd window.
- **Limits of this measurement.** Localhost, software encoders only, canvas capture instead of a screen capture, no loss, a single pair. It says nothing about how long a real 1080p screen keyframe takes to leave a loaded uplink (**inference**: a few hundred ms at a few Mbps), nor about a hardware decoder's start-up on the viewer. The localhost estimate also stays high through any restart, so the *collapse* ADR 2 recorded when a later description re-seeds a running connection did **not** reproduce here. That result stands on the ADR's own measurement of a live connection (Chromium 153), and this run neither confirms nor contradicts it.

## The bandwidth estimate

- **Where the seed goes in.** `x-google-start-bitrate` is read per codec by `GetBitrateConfigForCodec` (W: `media/engine/webrtc_media_engine.cc`): present and positive gives `start_bitrate_bps`, otherwise `-1`, "unchanged". `ApplyChangedParams` runs it whenever the send codec changes, and hands the result to `SetSdpBitrateParameters` on the transport controller. **Source-read.**
- **When it restarts the estimate.** `RtpBitrateConfigurator::UpdateWithSdpParameters` (W: `call/rtp_bitrate_configurator.cc`) only restarts when the start bitrate "is set, and different from the old value", and its comment says why: "setting the same remote description twice shouldn't restart bandwidth estimation". **Source-read.**
- **What follows for a codec switch.**
  - The estimate belongs to the connection (the transport controller), not to the send stream, so recreating the stream does not reset it. **Measured** (estimate unchanged) and source-read.
  - On the `setParameters` path the new codec is looked up in the negotiated codecs. Our seed went on every media codec of the screen's m-section in the first remote description, with one value, so the new codec carries the same value as the old, and no restart is expected. **Inference** from the source; the run above agrees but could not show a collapse either way.
  - A renegotiation without the seed leaves `start` at `-1` for every codec, so nothing restarts. Writing a seed into a later description is what restarts it (a different value restarts it by the source; the same value is the case ADR 2 saw collapse, which the source comment says should not, so the mechanism there is **not established**). Keep what `#forSenders` does today: seed only when `link.pc.remoteDescription` is unset.
  - One consequence for later: after an unseeded description the stored "old value" becomes `-1`, so a seed added later would count as a change.
- **Recommendation.** A codec switch does not seed, re-seed or change `withStartBitrate`. No code is needed for the estimate. A test that a switch leaves the remote description's start bitrate alone would document it.

## Stickiness: what the next negotiation does to a `setParameters` pick

This is the part to design around.

- **Chromium clears an encoding's `codec` whenever a new set of negotiated codecs no longer contains it by exact match.** In `SetSenderParameters` (W: `media/engine/webrtc_video_engine.cc`), for each encoding with a `codec`, the negotiated codecs are searched with `IsSameRtpCodec` (the full parameter set, *not* the level-ignoring match used when `setParameters` is validated); if there is no match, the code comments "The requested codec has been negotiated away, we clear it from the parameters" and resets `encoding.codec`, so the sender returns to the first negotiated codec. **Source-read.**
- **It bites us.** `getParameters().codecs[]` for the screen carries the seeded fmtp, so the picked codec reads `{mimeType: "video/VP9", sdpFmtpLine: "profile-id=0;x-google-start-bitrate=2700"}`. A later description (the polite side's own offer, a camera or audio change, an ICE restart) is not seeded, so its VP9 is `profile-id=0`, and the match fails. **Measured** in Chromium 156 with the seed: `setParameters` to VP9, then a plain re-offer, and the sender was back on AV1 with `encodings[0].codec` empty. Without the seed the pick survived the same re-offer, and so it did with the seed when `setCodecPreferences` had been set to VP9 first (that order simply makes VP9 the first codec).
- **Firefox keeps it.** **Measured** in Firefox 155: after `setParameters` to VP9 and a re-offer, the sender stayed on VP9 and `getParameters().encodings[0].codec` still read `video/VP9`. Firefox does not seed, so this run does not exercise the mismatch above.
- **So the recommended mechanism is a pair of calls**, each of which covers the other's gap:
  1. `setCodecPreferences` with the demoted order (AV1 out or last) on each video transceiver, so any later description, whoever offers, lands on the same codec; and
  2. `setParameters` with `encodings[0].codec` for the immediate switch, without waiting for a negotiation.

  `setCodecPreferences` alone changes nothing on the wire until an offer happens. `setParameters` alone is undone by the next unseeded description in Chromium.

## What in our code resets, or needs care

Line numbers are for `src/lib/mesh.ts` at the time of writing.

1. **Codec preference is applied once, at transceiver creation.** `#prefer` (l. 1007) is called only from `#addSlot` (l. 995), with `orderCodecs(this.#codecs.send, link.remoteCodecs)`. A switch needs (a) a streamer-wide "demoted codecs" input to `orderCodecs` in `src/lib/codecs.ts` (it ranks by `VIDEO_CODEC_PREFERENCE`; demotion would need to drop or rank last), (b) a loop that re-applies `#prefer` to every video transceiver of every link, and (c) the same input in `#addSlot`, so a viewer who joins mid-share, and a camera or screen added later, are offered the demoted order from their first offer. Without (c) a new pair would start on AV1 and have to be switched at once.
2. **The `setParameters` call must go through the sender's tuning chain.** `#tune` (l. 1051) serialises one `setParameters` per `link.tuning[slot]` promise, and `#applyRung` (l. 1062) calls `getParameters()` and writes back `{...parameters, encodings: [{...first, ...wanted}]}`. A parallel `setParameters` for the codec would race it (the spec rejects a `setParameters` whose `getParameters` transaction is stale). The codec change belongs in that chain. Also, `unchanged` there compares only `maxBitrate`, `maxFramerate`, `scaleResolutionDownBy` and the degradation preference, so a wanted codec would need its own comparison. The existing spread (`...first`) keeps an already-set `codec` across later rung changes, so ordinary steps do not undo a switch (**measured**: Chromium echoes the picked codec in `getParameters()` after the set).
3. **Bandwidth seed.** No action (above). `#forSenders` (l. 1769) must not start seeding later descriptions, and nothing in a switch should call it differently.
4. **The controller window.** `state.window` (a `LadderState` field, `src/lib/quality.ts` l. 353) is the last `WINDOW_SAMPLES` readings, and `nextRung` steps down when the last `DOWN_SAMPLES` (2) are `pressured`, which includes `limit === "cpu"`. After a switch the window still ends in the AV1 CPU-limited samples. The next reading is 4 s later and the reason is the encoder's current one, so a single clean reading breaks the run; but a reading taken while the encoder restarts could be wrong in either direction (inference; the 40 ms trace here showed the encoder's `targetBitrate` dipping from 3.0 to 2.5 Mbps for about two seconds after the switch before recovering). The existing template is the resume path (`#sendSlot`, l. 1036): `Object.assign(state, freshLadderState(rung), { readings: 0, last: undefined })`, which empties the window, restarts the warm-up ignore (`readings`), and sets `last` so the next `sendBitrate` starts clean. A codec switch should do the same but **keep the rung**, and (a choice, not a fact) probably keep `backoff` and `limited`, since a failed probe's wait and a pair's own-link ceiling are not about the codec. The next controller call is then a warm-up reading, not a step-down on stale CPU pressure. `state.codec` (l. 1456) updates from the sample, so nothing else is needed for it.
5. **The telemetry windows.** `QualityCollector.observe` (`src/lib/quality-collector.ts`, l. 121) already ends a window when a reading's codec differs from the window's, for senders and receivers alike, and starts the next from that reading ("QP is only comparable within one codec", ADR 2). Nothing breaks. Three things to know: that row has `trigger: "window"` and no change reason (`RUNG_REASONS` has no codec entry; a "codec switch" cause for the modal and the admin timeline, listed as open in map #125, would be a new reason, and `rungChanged` is not called for it); a switch has no rung change, so `telemetry.reset` (the call that drops a window, used by `#sendSlot`) is *not* wanted, because the codec cut already does what is needed; and ADR 2's "time to settle" already ignores a window a codec change cut short, so a mid-share switch will not read as a pair that never settled. The viewer's own receiver window also closes on the same change, since `inbound-rtp.codecId` changes (**measured**).
6. **A viewer is not told.** `setParameters` changes nothing in the SDP, so the receiving page learns of the switch only from its stats (`codecId`). The step note (`quality` signal) carries a label, bitrate, reason and cause but no codec; if the modal is to say "switched to VP9 because the streamer's computer was struggling", the streamer has to send it (a new optional field on the existing `quality` payload, no new signal kind). The receiver's `inbound-rtp` codec is already used for the modal's codec chip.
7. **Perfect negotiation, if the fallback runs.** `#offer` is reached only through `onnegotiationneeded` (l. 959), and `setCodecPreferences` does not raise it, so the fallback needs an explicit `#offer(link)` when the link is stable and a deferred one otherwise (a pending local offer, or a `makingOffer`). A collision resolves as for any other offer (the polite side rolls back, the impolite side ignores). Because `#prefer` has already set the new order, whichever offer next goes out carries it, so the deferred case needs no retry state of its own. The first-negotiation caveat in `mesh.ts`' header (the polite side adds its transceivers after answering) means a switch triggered before a pair's first negotiation completes needs only `#prefer` and no offer.
8. **`orderCodecs` and the answer.** In the loopback the answerer, with no preferences of its own on a receiving transceiver, answered in the offer's order, so the offerer's order decides the sender's codec (**measured**; the viewer's page in the Mesh also sets no preferences on a transceiver it only receives on, but that was not run). ADR 2 trims only what the peer cannot decode, and the whole list stays in the negotiated send set, which is what lets `setParameters` pick any fallback. Keep that: rank the demoted codec last rather than dropping it, so a later `setParameters` or a switch back stays possible. The map's rule that a streamer stays off AV1 until the share ends is a rule about when to promote again, not something the SDP has to enforce.

## Several pairs at once (a streamer with up to 9 viewers)

- **Each pair is independent.** There is one `RTCPeerConnection` per pair (ADR 1), so each has its own congestion controller and its own encoder per sender; a streamer with 9 viewers and a screen and a camera runs up to 18 video encoders. A switch is therefore a per-sender operation, run for every sender (the map settles that screen and camera both switch). The 9 estimates are separate, so none interacts with another.
- **`setParameters` is local.** It sends nothing: no `signal` step, no offer and no answer. The renegotiation fallback costs 9 offers and 9 answers (Chromium's largest offer is about 24 KB, ADR 4; `SIGNAL_RATE_LIMIT` is 400 per 10 s), which fits but adds 18 messages and the glare handling.
- **CPU and uplink at the moment of the switch (inference, not measured).** Each restart creates a new encoder and the first frame out of each is a keyframe, so 9 screen senders emit a keyframe each at about the same time, on a machine that is CPU-limited by definition and on an uplink the `UplinkBudget` shares between them. The estimator and pacer should smooth the burst, and the switch is a one-off, but a streamer already at a CPU limit pays the restart cost first. Staggering the switches by a short interval (say a few hundred ms per sender, screens first) bounds that peak at one restart at a time at almost no cost to the viewers. That is a suggestion; I have no measurement that says it is needed.
- **A later viewer pays nothing:** the demoted order is in their first offer (item 1c above).

## How often it can happen

Per switch, per video sender: one encoder restart, one keyframe, no signalling on the `setParameters` path, a reset of the controller's window. The viewer-visible cost measured here is within one or two frame intervals. On those numbers a codec switch is much cheaper than the behaviour it replaces (a minute at 720p and 6 to 9 fps, the 2026-10-21 session in the map). Under the map's settled rules (switch on a sustained CPU limit, stay off AV1 until the share ends) it can happen at most once per share and sender, so the cost is bounded without any rate limit. A flip-flop guard is only needed if the rules ever allow going back to a demoted codec.

## Not established

- **Real-network cost.** The size of a 1080p screen keyframe and how long it takes on a loaded uplink; how a hardware decoder behaves on the first packet of a new payload type. Both need a field measurement (the telemetry already records `keyframes` and `freezes`).
- **The ADR 2 estimate collapse.** Not reproduced here; the mechanism is not established (the source says an identical start bitrate should not restart the estimate).
- **Safari.** Absence is from BCD and release notes. I did not run Safari.
- **Hardware encoders.** Only software encoders were available, and neither `encoderImplementation` nor `powerEfficientEncoder` appeared in the sender stats of this run. webrtc-stats says both "MUST NOT exist unless exposing hardware is allowed" (https://w3c.github.io/webrtc-stats/, `RTCOutboundRtpStreamStats`), a condition a canvas-capture test page does not meet. Which fields a real screen share exposes bears on #127, not on this ticket.
- **Staggering.** Whether it is needed is a guess.
- **Edge.** Taken from BCD ("mirror" of Chrome) and not run.
