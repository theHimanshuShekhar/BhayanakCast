# Which codec should a CPU-limited streamer fall back to, and what does each cost?

Research for ticket #127, part of map #125 ("Pick video codecs by what the streamer's machine can afford"). Researched 2026-10-21 and 2026-10-22. It builds against ADR 2 (codec order AV1, VP9, H.264, VP8 per pair through `setCodecPreferences`; a CPU limit is *pressure*; the quality telemetry), ADR 1 (mesh: one encode per viewer, up to 9), `src/lib/codecs.ts` and `src/lib/quality.ts`. The app's loads: screen shares up to about 3.7 MP at up to 60 fps, 1080p30 targeted at 2.7 Mbps and 1080p60 at 5.4 Mbps (ADR 2 seed), cameras 360p15.

## Answer in one paragraph

When a software AV1 encoder is CPU-limited, **go straight to H.264, not one step down to VP9**. Software VP9 and VP8 are not reliably cheaper than software AV1 on screen content (published measurements disagree on the order, and libwebrtc already runs AV1 screen shares at its fastest libaom speed), while H.264 is the only codec that is consistently cheap: hardware H.264 is close to free where Chromium uses it (Windows, macOS), and OpenH264 is the cheapest software encoder in every measurement found. H.264's text is acceptable for screens at this app's bitrates (above about 1 Mbps; the weak spots are scrolling and low bitrate), but it needs several times the bitrate of AV1 or VP9 for the same sharpness. Chromium does **not** adapt AV1's speed for screen shares: the screen-share speed controller has a single level, already at the fastest setting, so the only relief is fewer pixels or frames, or another codec. By Chromium's own defaults, **desktop Chromium on Windows never uses a hardware AV1 encoder for WebRTC** (`WebRtcAV1HWEncode` is off by default on Windows), macOS has none, and Linux hardware encode is off by default, so a Chromium AV1 streamer is software-encoded almost everywhere, whatever GPU it has. Firefox encodes AV1 (since 136, libaom, software only) and H.264 through OpenH264 (a downloaded plugin), and reports no `qualityLimitationReason`, but does report `totalEncodeTime` and `framesEncoded`, which is enough to build a CPU trigger.

## Comparison

"Cost" is encoder CPU for one stream of screen content; the mesh multiplies it by the number of viewers (up to 9) and the camera adds one more per viewer.

| | AV1 | VP9 | H.264 | VP8 |
| --- | --- | --- | --- | --- |
| Chromium software encoder | libaom, screen mode, speed 10 for key frames and 11 for all others, no further speed to give | libvpx, screen-content tuning, speed 9 at 1080p and above | OpenH264, `SCREEN_CONTENT_REAL_TIME`, **one thread** per encoder, Constrained Baseline only | libvpx, fast real-time speed (-6 at the codec's init; the complexity setting moves it to about -10) |
| Chromium hardware encoder used by default | **No on Windows** (feature off), no on macOS, Linux off by default | Windows: Media Foundation lists VP9 if a hardware MFT exists (Intel silicon can; whether its driver ships one was not checked); none on macOS; Linux off | **Yes on Windows and macOS** (Media Foundation / D3D12; VideoToolbox); Linux off | No |
| Measured CPU, screen text, ~1.5 MP ~24 fps, encode plus decode in one tab, encoder implementations not stated (HackerNoon, Mar 2025) | 175% | 198% | **130%** | 179% |
| Measured software CPU, 720p30 camera stress, Windows ThinkPad, Chrome 135 (Anguenot, Apr 2025) | 225% (15 ms/frame) | 180% (18 ms) | OpenH264 **60%** (14 ms); hardware **20%** (11 ms) | 110% (10 ms) |

## Findings

### 1. What the Chromium encoder actually is, per codec (Source-read)

Edge 155 shares Chromium 155's source (branch 8059).

- **AV1.** `LibaomAv1Encoder` (`modules/video_coding/codecs/av1/libaom_av1_encoder.cc`, branches 7871, 8059, main). In screen-share mode it sets `AV1E_SET_TUNE_CONTENT = AOM_CONTENT_SCREEN` and palette on. Threads: with more than 1280x720 pixels and more than 8 cores it uses 8; with at least 640x360 and more than 4 cores it uses 4; so a 6-core machine runs 4 libaom threads for each viewer's encoder. Its comment says the real-time speed range is 6 to 10 and "Speed 11 is used for screen sharing". `GetEncoderInfo` reports `implementation_name = "libaom"` and `is_hardware_accelerated = false`.
- **VP9.** `LibvpxVp9Encoder`: screen mode sets `VP9E_SET_TUNE_CONTENT 1` and a minimum quantizer of 8. Default performance flags put speed 9 on all layers from 1920x1080 pixels up, with denoising off, "since this is very CPU intensive". Threads: 4 above 1280x720 with more than 4 cores.
- **H.264.** OpenH264. `iUsageType = SCREEN_CONTENT_REAL_TIME` for screen shares. `iMultipleThreadIdc` is **1 (a single thread)** unless the `WebRTC-VideoEncoderSettings/encoder_thread_limit` field trial is set (`h264_encoder_impl.cc`, `NumberOfThreads`). libwebrtc encodes only Constrained Baseline ("We only support encoding Constrained Baseline Profile", `h264.cc`) and OpenH264's own README lists only Constrained Baseline, so there is no CABAC and no B-frames. The software formats are advertised at level 3.1. Chromium offers OpenH264 only when the build has `ENABLE_OPENH264` and FFmpeg video decoders and `kOpenH264SoftwareEncoder` is on (default on) (`media/webrtc/webrtc_features.cc`); builds without them (inference: some distro Chromium) would have **no H.264 at all**. The same check disables the hardware H.264 path on desktop, because hardware H.264 requires the software encoder as its fallback (`UseH264AcceleratedEncoderForWebRTC`, `webrtc_util.cc`).
- **VP8.** `LibvpxVp8Encoder`, `cpu_speed` -6 at normal complexity.
- **Cost per viewer.** The mesh runs one encoder instance per viewer. All of these are per-instance costs, so nine viewers are nine libaom (4 threads each) or nine OpenH264 (1 thread each) instances. Inference.

### 2. Does Chromium's software AV1 adapt its speed? No, not for screen shares (Source-read, plus inference)

- **What exists.** libwebrtc has an `EncoderSpeedController` (`api/video_codecs/encoder_speed_controller.h`), used by `LibaomAv1Encoder` through `LibaomSpeedConfigFactory`. It watches encode time and QP per frame and moves along an ordered list of speed levels. Dynamic speed is **off by default on branch 7778 (Chrome 148)** (`encoder_speed_experiment.cc`: field trial `WebRTC-EncoderSpeed`, parameter `dynamic_speed` defaulting to false) and **on by default on branches 7871 (150), 8037 (154), 8059 (155) and main**. Branch 7827 (149) could not be read, so the flip landed in 149 or 150.
- **What it has to work with for a screen share.** The default complexity for AV1 is `High` for camera and `Low` for screen share. `Low` gets two levels, and screen share removes one (`num_levels = max(1, num_levels - 1)`), leaving **one level: speeds {10, 11, 11, 11}** for {key frame, normal frame, intermediate, non-reference}. A one-level controller cannot go faster or slower. Before the controller existed (and with it off) the static path also returned speed 11 for screen shares (`GetCpuSpeed`). Camera streams get eight levels and can move.
- **Meaning.** The Edge 155 streamer ran the fastest libaom real-time speed already. There was nothing left for the encoder to cut except pixels and frames. That is done by libwebrtc's overuse detector: when the average encode time exceeds 85% of the frame interval (`CpuOveruseOptions`, `high_encode_usage_threshold_percent = 85`, `overuse_frame_detector.h`), it asks the source for a lower resolution or frame rate according to the sender's `degradationPreference`. At 60 fps the threshold is 14.2 ms per frame, at 30 fps 28.3 ms. This is what produced the session's 720p and 6 to 9 fps.
- **Caveat.** A Chrome field trial can set `WebRTC-EncoderSpeed` (per-codec `*_screenshare` complexity); the defaults above are what the source ships. Not observable from outside.
- **Pixel-rate arithmetic (inference).** 1080p30 = 62 MP/s, 1080p60 = 124 MP/s, a 3.7 MP share at 60 fps = 222 MP/s. Each viewer repeats it: nine viewers at 3.7 MP and 60 fps is about 2 gigapixels per second of software encode. No published per-core throughput for libaom speed 11 on screen content was found, so a safe viewer count for a given CPU cannot be derived from sources; it can only be measured on the streamer's machine (hence the mid-share trigger).

### 3. Published cost measurements

All numbers below are from the sources named; none was reproduced here.

- **Chrome team, AV1 vs VP9 in libwebrtc (Chrome 113, libaom 3.6.0, 2023).** "Compared to VP9 speed 7, AV1 Speed 10 provides 45% better compression while running 35% faster" for screen sharing; for camera, "12% better quality at the same bandwidth while running 25% faster on desktops" (https://developer.chrome.com/blog/av1, last updated 2023-05-02). VP9 speed 7 is slower than the speed 9 libwebrtc uses for VP9 at 1080p, so the 35% does not carry over to today's VP9 default.
- **Hopp / LiveKit, libwebrtc without a browser, macOS M1 and Windows i5-8400, 30 fps, static screen content (2025-06-21, https://www.gethopp.app/blog/screensharing-encoders-compared).** Encoder CPU at 1080p (simulcast on / off): macOS VP8 52.7/50.3, VP9 52.2/57.6, AV1 60.9/60.8, H.264 43.1/39.5; Windows VP8 112/91.5, VP9 113/111, AV1 114/112, H.264 113/83. At 1440p macOS: VP8 63, VP9 63, AV1 74. So on the Mac AV1 costs about 17% more than VP8/VP9 and 41% more than H.264, and on the Windows desktop CPU the same as VP8/VP9; H.264 is lowest on macOS and only lower than the others on Windows without simulcast. Hardware encoders were not stated. Bitrates were chosen per codec to land at VMAF 96 to 97: at 1080p with 33 Mbps up, VP9 0.20, VP8 0.40, H.264 0.55 Mbps (macOS and Windows; AV1 not reported).
- **Anguenot, Chrome 135 (2025-04-16, https://www.webrtc-developers.com/comparison-of-webrtc-codecs-for-video-and-screen-sharing/).** The camera stress table in the comparison above (720p30, a ThinkPad and a Mac mini M2 Pro, encode plus decode in the tab). For 1080p10 screen share with `contentHint = detail` his judgement is that AV1 is best at low bitrate (scrolled text readable almost instantly), VP9 good at reasonable bandwidth, OpenH264 "consistent and degrades gradually", VP8 weakest "apart from hardware H264", and on one Lenovo the hardware H.264 was "completely unusable" for scrolling text even at high bitrate while another vendor's laptop was fine.
- **Beskrovnov, Chrome (2025-03-25, https://hackernoon.com/how-good-is-webrtc-screen-sharing-really-i-put-4-codecs-to-the-test).** CPU at about 1.5 MP and 24 fps, encode plus decode in the tab: motion AV1 287%, H.264 213%, VP8 270%, VP9 364%; text AV1 175%, H.264 130%, VP8 179%, VP9 198%. Browser version, machine and which encoders ran are not stated. With resolution prioritized on scrolling text, "AV1 pulls far ahead of the other codecs" at higher bitrates.
- **Meta, AV1 with libaom vs OpenH264 (https://atscaleconference.com/av1-improving-rtc-video-quality-at-scale/, 2023-11-29).** "Up to an 80% BD-BR savings" on a screen share (same quality for one fifth of the bitrate), credited to palette mode and intra block copy; about 30% on talking-head video. AV1 is "still more CPU-intensive by approximately a factor of five than the H.264 implementation we're currently using, even when used in low-complexity mode and real-time setting". Meta's 2026 update (https://engineering.fb.com/2026/06/22/video-engineering/adopting-av1-for-real-time-communication-rtc-meta/) says it replaced the open-source encoder with an internal low-complexity one (the open-source one used 14% more power than H.264 on a Pixel 8), lowers the encoder preset first when the device nears its real-time limit and **then switches to H.264**, which is the same order this ticket recommends.
- **Jitsi (2024-12-17, https://jitsi.org/blog/av1-and-more-how-does-jitsi-meet-pick-video-codecs/).** AV1 "was the best codec for screen sharing on all platforms"; H.264 "showed minimal CPU usage only where hardware acceleration was supported" and software H.264 at 4K or for screen sharing was much more costly. Its CPU-overuse handling: when the outbound stats indicate a CPU limitation, "the client iteratively switches to a lower-complexity codec" until the lowest-complexity codec benchmarked for that video type, and CPU use is measured from average encode time (`totalEncodeTime`). The measurements are screenshots; no numbers are quotable.
- **Reading the pile (inference).** Measurements disagree on AV1 vs VP9 vs VP8 ordering (they depend on machine, content, thread counts and which version of libaom). They agree that H.264 is the cheapest, and that VP9 is not a cheaper step down from AV1. The measured spread of AV1 over H.264 on screen text is 35% (HackerNoon) to a factor of five (Meta's low-complexity H.264 baseline).

### 4. Text sharpness: is H.264 good enough for screens?

- **Tools.** AV1's main profile includes palette mode and intra block copy for screen content (Meta; AOMedia tool description). IntraBC alone gave 27.1% bitrate saving in an IEEE study (https://ieeexplore.ieee.org/document/8416608/, seen only as a search snippet). OpenH264's screen mode has scene-change handling and long-term references but no palette or block copy; with Constrained Baseline only it has CAVLC, no B-frames and no 8x8 transform. VP9 in libvpx has only the screen-content tuning flag, no palette or block copy. Source-read plus Meta.
- **Chroma.** Every WebRTC profile Chromium exposes here is 4:2:0 (H.264 Baseline/Main/High, VP9 Profile 0, AV1 Profile 0 Main; `rtc_video_encoder_factory.cc` and the Media Foundation profile list), so coloured text fringes the same way in all four codecs. This does not separate them.
- **At this app's bitrates.** Anguenot found H.264 "did well above 1 Mbps but degraded quickly below"; this app targets 2.7 Mbps at 1080p30 and 5.4 Mbps at 1080p60, and Hopp's H.264 needed 0.55 Mbps for VMAF 96 to 97 on static content. So H.264 is **acceptable for static and slowly changing screens at the default and higher steps**, and visibly worse when a pair steps down to a low-bitrate step or when text scrolls. Hardware H.264 also varies by driver: Anguenot's Lenovo was unusable for scrolling text while another laptop was fine (one anecdote, cause unknown). Inference: the pair-level quality controller handles the low-bitrate case, so H.264 does not need to be rejected for screens.
- **The cost of the downgrade.** A switch from AV1 to H.264 should be expected to raise the bitrate needed for the same sharpness by a large factor on text (Meta up to 5x; Hopp about 2.75x over VP9 on static content), so a pair that was bitrate-comfortable on AV1 may be held on a lower step on H.264 on a thin link. The quality controller already measures that per pair.

### 5. Hardware encoders: who has them, and does Chromium use them for WebRTC?

**Chromium, by OS (Source-read, `main` 2026-10-21 unless a branch is named).**

| OS | Hardware encoders that Chromium can offer to WebRTC | Defaults that decide it |
| --- | --- | --- |
| Windows | Media Foundation: H.264, VP9, AV1 (any hardware MFT); D3D12: H.264, HEVC, AV1. Both are on by default as encoders (`kMediaFoundationVideoEncodeAccelerator`, `kD3D12VideoEncodeAccelerator`) | **`kWebRtcAV1HWEncode` is off by default on Windows** (and on in the code for other OSes), in branches 7778, 7871, 8037, 8059 and `main`: AV1 profiles are put in `disabled_profiles_`, so no hardware AV1 for WebRTC. A Chromium commit message (August 2025, via search, not read directly) says D3D12 AV1 for WebRTC "will be rolled out later with corresponding ISV". Also `kPlatformH264CbpEncoding` is off on Windows, so the hardware H.264 is advertised as Baseline/Main/High, not Constrained Baseline. Temporal layers for hardware AV1 and VP9 are off (`kMediaFoundationAV1L1T2Support` etc.); the app uses none |
| macOS | VideoToolbox: **H.264 and HEVC only** (`vt_video_encode_accelerator_mac.mm`) | none for VP9 or AV1 |
| Linux | VA-API: H.264, VP8, VP9, AV1 | **`kAcceleratedVideoEncodeLinux` is off by default**, so Linux Chrome and Edge are software-only unless a field trial or flag turns it on |
| any | A VEA is used only when the codec has a listed profile within its size limits; below 360p (270p for AV1) Chromium forces software (`kForceSoftwareForRtcLowResolutions`), so the 180p camera step is software | |

Consequence (inference, strong): **a Chromium streamer on Windows today is software-AV1 whatever its GPU.** That agrees with #126's `powerEfficient` rule (true iff a hardware profile is listed): `encodingInfo` for AV1 returns false by default on Windows, macOS and Linux. The friends-session premise that Edge 155's AV1 was software is therefore likely true, though still not read from its telemetry (the rows do not record the encoder). Where a field trial enables `WebRtcAV1HWEncode`, the rest of this table says which GPUs would have an encoder to use.

When a hardware encoder is used, Chromium passes the content type to it. On Intel under Windows the Media Foundation encoder is told `eAVScenarioInfo_DisplayRemoting` for screen shares, which turns on AV1's screen-content tools; for other vendors that is a TODO in the source (crbug 336592435). Source-read, `media_foundation_video_encode_accelerator_win.cc`.

- **NVENC session cap.** The NVIDIA matrix lists "Max # of concurrent sessions" as 12 for GeForce parts (read through a summariser; the page has no footnote). A mesh streamer with 9 viewers and a camera can ask for 18 encoders. What Chromium does at the limit (fall back to software per encoder, or fail) was not found. #126 saw a secondary claim of a 3 to 4 encoder cap; I could not confirm either figure from a primary page for this app's setup. Not verified.
- **Hardware H.264 is the one hardware encoder that is nearly universal**: every vendor above, Windows and macOS in Chromium. That makes H.264 the fallback with a real chance of costing almost nothing (Anguenot: 14% to 20% CPU vs 54% to 60% for OpenH264).

### 6. Firefox (Source-read: Firefox `main`; vendored libwebrtc updated 2026-10-20)

- **AV1.** Encodes AV1 in WebRTC since **Firefox 136** (bug 1944878, target 136; initial support in 135 behind `media.webrtc.codec.video.av1.enabled`, now `true`; for sending, "both singlecast and simulcast are supported"; also Android). The encoder is libwebrtc's libaom (`CreateLibaomAv1Encoder` in `WebrtcVideoCodecFactory.cpp`); **software only**. The platform encoder path (`WebrtcMediaDataEncoder`) supports H.264, VP8 and VP9 only, with AV1 and HEVC a TODO (bug 1980201). AV1 is not Firefox's preferred codec by default (`media.webrtc.codec.video.av1.experimental_preferred` false), which does not matter for this app, which sets its own order. Firefox's vendored libaom wrapper contains the same screen tuning and speed-controller code as Chromium's `main`, and Firefox's screen shares use `MAINTAIN_RESOLUTION` by default. So the AV1 CPU behaviour in finding 2 should hold for Firefox (inference; the release build's libwebrtc is older than `main`).
- **H.264.** The default (`media.webrtc.encoder_creation_strategy` = 0 on desktop) is libwebrtc's software encoder, which for H.264 is **OpenH264 loaded through a GMP plugin** that Firefox downloads. Only if that plugin is unavailable does it fall back to the platform encoder (`createPlatformEncoder`, which can be hardware: Media Foundation, VideoToolbox). On Android the strategy is 2 (platform hardware first, then software). #126's run saw no H.264 in `getCapabilities` on a Firefox 155 profile that had no OpenH264 plugin downloaded. VP8 and VP9: libvpx. So on desktop Firefox every codec is software, H.264 is the cheapest.
- **Signals.** Firefox reports no `qualityLimitationReason` (its `RTCOutboundRtpStreamStats` IDL has none; MDN marks it unsupported there), no `encoderImplementation` and no `powerEfficientEncoder` (#126). It **does** report `totalEncodeTime` and `framesEncoded` (`dom/webidl/RTCStatsReport.webidl`; populated in `RTCRtpSender.cpp`), the same inputs Jitsi uses and libwebrtc's own overuse detector uses. So a Firefox CPU trigger is possible: the mean encode time per frame over a window (Δ`totalEncodeTime` / Δ`framesEncoded`) against the frame interval, using libwebrtc's own 85% threshold. A frame-rate drop (`framesPerSecond` below the capture rate) is the second visible sign, because Firefox's screen shares hold resolution and shed frames. Whether Firefox runs libwebrtc's overuse detector at all on screen shares was not checked (inference only).

### 7. Fallback order and the trigger

- **Recommended order on a sustained CPU limit (Inference from 1 to 6):** AV1 → **H.264** (hardware if Chromium lists it, else OpenH264) → VP9 → VP8. Skip VP9 on the first step; use VP9 and VP8 only where H.264 isn't available: a build without OpenH264 (some Chromium builds; a Firefox without the plugin), or a viewer that can't decode it (per pair). Among those two, VP8 is the cheaper in three of the four measurements (Anguenot Windows 110% vs 180%, Mac 38% vs 80%, HackerNoon text 179% vs 198%; equal in Hopp).
- **One step or straight to the cheapest?** Straight to H.264. VP9 is not reliably cheaper than software AV1, and the speed that would have made AV1 cheaper is already used up. A one-step-down policy would spend a second CPU-limited minute on VP9 and then switch again.
- **If H.264 is also CPU-limited** (software on a weak CPU with many viewers), the next lever is pixels and frames, which the quality ladder already does; no codec is cheaper.
- **Up-front pick (builds on #126).** On Chromium, `powerEfficient` false for AV1 now means software AV1 on Windows, macOS and Linux by default. Whether to start those streamers on H.264 or on AV1 with the mid-share switch as the net is a decision for the spec tickets. The data they need: software AV1 is acceptable for few viewers and fewer pixels (the friends' session had two viewers and hit the limit within 30 s), its text is much better than H.264's, and the cost grows with viewers × pixels × fps. `encoderImplementation` ("libaom" vs a hardware name) and `powerEfficientEncoder` from #126 give the telemetry for what actually ran.
- **Mid-share trigger.** Chromium: `qualityLimitationReason === "cpu"` sustained (already the controller's pressure signal). Firefox: mean encode time per frame as in finding 6. The switch itself is #128's `setParameters` path.

## Not verified

- **Field trials.** Whether Chrome or Edge 155 or 156 on real machines has `WebRtcAV1HWEncode`, `AcceleratedVideoEncoder` (Linux) or `WebRTC-EncoderSpeed` overridden by a server-side trial. The defaults were read from source only; branch 8078 (Chrome 156, current stable) and branch 7827 (149) could not be fetched. The friends' Edge 155 AV1 encoder implementation remains unconfirmed.
- **Absolute software AV1 cost** for screen content at libaom speed 11 per core or per pixel rate; no primary number exists in what I found, only the ratios above. None of the measurements is of a mesh with several encoders at once.
- **Hardware behaviour on real GPUs.** No hardware encoder was run (all measurements are cited, none mine). The Windows hardware H.264 quality anecdote (Anguenot) is one machine. What Chromium does when NVENC's 12-session cap (as read from NVIDIA's page) is exceeded was not found; the 3 to 4 figure in #126 is unconfirmed.
- **AMD and the VP9 hardware column** rest on Wikipedia and Tom's Hardware, not an AMD page. The NVIDIA page was read through a summariser.
- **Firefox:** which Firefox release first contains the speed-controller code (the vendored copy at `main` has it; a release may not); whether Firefox applies libwebrtc's CPU overuse detection to screen shares; the exact conditions that make the OpenH264 plugin unavailable.
- **OpenH264 level 3.1** is what the software encoder advertises, while this app sends up to 1080p60 and above; whether any decoder (Firefox, OS decoders) enforces the level was not tested.
- **Chromium commit 4c2d532** (the August 2025 note that D3D12 AV1 for WebRTC is behind `WebRtcAV1HWEncode`) was seen through a search snippet; the commit page could not be fetched.
