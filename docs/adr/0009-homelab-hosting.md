# 9. Homelab hosting with Docker Compose and Cloudflare Tunnel

Date: 2026-09-27 · Status: accepted

## Decision
Deploy on the homelab as Docker Compose: `app` (TanStack Start Node server with WebSocket) and `postgres`. Expose it publicly through a Cloudflare Tunnel (`cloudflared`), which provides TLS and WebSocket support without port forwarding.

## Consequences
- The server handles only HTTP, WebSocket signalling and DB work; media is peer-to-peer (ADR 1), with Cloudflare TURN as relay (ADR 3). Home uplink is not a media bottleneck.
- Availability depends on home uptime. A restart doesn't end rooms: they're restored from Postgres and clients reconnect within a grace, losing only chat and the feed (ADR 4, 2026-10-02 addendum).
- Cloudflare Tunnel may close idle WebSockets, so the client and server exchange heartbeats (ping every ~30s).

## Addendum: deployment and storage (2026-09-27)
- Deployed as a **git-backed stack on Dockhand**, which builds from this repo's compose file on the dockhand LXC, like llm-gateway. The app binds to the LAN IP.
- Uses the homelab's **existing shared cloudflared**, with public hostname `cast.bhayanak.net` pointing at the app's LAN port. This stack has no cloudflared service of its own.
- Postgres data lives on a **local Docker volume**, never on the NAS CIFS share. Postgres needs working fsync, locking and Unix permissions, which CIFS doesn't provide, so running it there risks silent corruption.
- A small sidecar writes a nightly compressed `pg_dump` and rsyncs the dump directory to the NAS CIFS share, keeping 14 days. The raw data directory is never rsynced, because a live copy isn't restorable.

## Addendum: one origin for pages and the socket (2026-09-28)
The realtime WebSocket (`/ws`) runs on the same port and hostname as the app, so the single tunnel public hostname `cast.bhayanak.net` carries both HTTPS pages and `wss://…/ws`. No second tunnel route is needed. Don't override the tunnel's HTTP Host header: the socket's same-origin check compares the page's Origin with the Host it receives.

## Addendum: client IP behind the tunnel (2026-09-28)
The app is published on the LAN IP, so a LAN client can reach it directly and send its own `cf-connecting-ip`. The header is trusted only when the direct peer is listed in `TRUSTED_PROXY_IPS` (the shared cloudflared host; required in production); from anyone else the socket address is the client IP. This covers the per-IP limit on anonymous sockets (ADR 20) and Better Auth's rate limiter, which reads only headers, so the production server rewrites `cf-connecting-ip` to the resolved IP before any handler runs. `pnpm dev` doesn't rewrite it.

## Addendum: the backup sidecar mounts the NAS itself (2026-09-30)
The sidecar's NAS directory is a Docker `cifs` volume of the `local` driver in the compose file, not a bind mount of a share the host mounts. Docker mounts it whenever the sidecar starts, so it needs no host fstab entry and survives reboots, and an unreachable share stops the sidecar instead of letting it write to an empty local mount point. The NAS account's credentials are stack variables. Postgres data stays on its local volume.

## Addendum: backup health must mean a recent backup (2026-10-02)
The sidecar's healthcheck no longer trusts an old "ok". The status file carries the finish time, and the check fails once it is older than `BACKUP_MAX_AGE_HOURS` (default 26), so a stopped schedule shows as unhealthy and not as healthy forever. `pg_dump` and `rsync` run under timeouts so a hung run fails and frees the run lock, and each run clears the temp files an interrupted one left. These are additions to the 2026-09-27 and 2026-09-30 decisions, which stand: local-volume Postgres, dumps rsynced to the NAS, and the Docker-mounted `cifs` volume. An unreachable NAS still stops only the sidecar; the app and `db` start (docs/deploy.md section 5).

## Addendum: environment validation fails closed (2026-10-02)
Only an explicit `NODE_ENV=development` or `test` gets the placeholder secrets and the test-only sign-in (`E2E_AUTH=1`). Anything else (unset, empty, unknown) is validated as production: a deploy that loses `NODE_ENV` fails at startup, listing the missing secrets, instead of booting with the development defaults; an unknown value such as `staging` is refused. The e2e server, which used to run with `NODE_ENV` unset, now sets `NODE_ENV=development` explicitly (`playwright.config.ts`).

## Addendum: security headers and caching (2026-10-02)
The production server (`server.prod.ts`) sets the headers; `pnpm dev` sets none, since Vite's HMR needs inline scripts and its own socket.
- **Content-Security-Policy on every response:** `default-src 'self'`; scripts `'self'` plus a per-request nonce; styles `'self' 'unsafe-inline'`; images `'self' data: https://cdn.discordapp.com`; media `'self'` (no `blob:`: video plays MediaStreams through `srcObject`, which CSP doesn't check, and thumbnails come from `/api/thumbnails`); fonts and connections `'self'`; `object-src 'none'`; `frame-ancestors 'none'`; `base-uri 'self'`; `form-action 'self'`.
- **No `unsafe-inline` for scripts:** TanStack Start renders inline scripts for hydration and streamed SSR state, and their content differs per request, so hashes can't cover them. The middleware makes the nonce and leaves it in `request.context`; the router reads it into `ssr.nonce` (`src/router.tsx`), and Start puts it on each inline script and in a `csp-nonce` meta tag for the browser's router. Styles keep `unsafe-inline` because React writes inline `style` attributes.
- **No `unsafe-eval`, no `data:` fonts:** the e2e run under the policy found two things that tripped it. Zod 4 probes for `new Function` before compiling object parsers, and a CSP reports that caught throw as a violation; pages therefore start with a nonced inline script (root route `head`, `src/lib/zod-jitless.ts`) that sets zod's `jitless` global before its module loads, so the browser parses the slow way while the server keeps the compiled parsers. Calling `z.config({ jitless: true })` from the app's own bundle was too late: the chunk holding zod and the schemas evaluates before the entry's own code. Vite inlined the smallest JetBrains Mono subset into the CSS as a `data:` URL; `build.assetsInlineLimit` now keeps `.woff`/`.woff2` as files, so `font-src` stays `'self'`.
- **Connections and sign-in:** `connect-src 'self'` covers the same-host WebSocket; STUN/TURN traffic isn't governed by `connect-src`. Discord sign-in is a navigation (the page asks Better Auth for the URL, then sets `location`), which none of these directives restrict.
- **Also on every response:** `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`, or `no-referrer` on `/join/*`, whose URL is a bearer token.
- **Caching:** HTML pages (they embed the session's loader data), `/_serverFn/*` and `/api/auth/*` send `Cache-Control: private, no-store`, as does any other app response that sets none of its own; thumbnails keep their `private` and ETag. Files in `/assets/` are content-hashed and get `public, max-age=31536000, immutable` (the static middleware sent no `Cache-Control` before); other static files, like the favicon, keep the default. Without this, one CDN cache rule would have let a shared cache serve one user's server-function answer to another.
- An error the app throws is answered by the same middleware as a plain 500 (logged as `http.unhandled`), so it carries the headers and `no-store` too.
- The WebSocket upgrade isn't a fetch response and is untouched.

## Addendum: the app's healthcheck reaches the database; secrets are host-visible (2026-10-02)
- The app's compose healthcheck calls `GET /api/health`, which runs `select 1` with a 3 s timeout and answers 200 or 503 (`src/server/health.ts`). It replaces Better Auth's `/api/auth/ok`, which never touched Postgres, so a lost database now shows as `unhealthy`. It is outside `/api/auth`, so the auth rate limiter doesn't count it, and it needs no session. Docker doesn't restart an unhealthy container (`restart: unless-stopped` acts on exits only), so this makes the outage visible in Dockhand rather than fixing it; the app's connection pool reconnects once Postgres is back.
- Secrets are visible to anyone with Docker access on the host: `docker inspect` shows the app's environment (`DATABASE_URL` carries the database password), and `docker volume inspect` shows `BACKUP_NAS_PASSWORD` in the `nas` volume's options. This is documented in docs/deploy.md ("Who can see the secrets on the host") and accepted: the alternatives (a credentials file or mount on the host) give up the git-backed, no-host-setup deploy.

## Addendum: the native-TypeScript runtime is guarded (2026-10-02)
`server.prod.ts` and everything it imports run unbundled under Node's type stripping, which can't run enums, namespaces or parameter properties, or an import of a type that isn't marked `type`. `tsconfig.json` now sets `erasableSyntaxOnly` and `verbatimModuleSyntax`, so `pnpm typecheck` refuses them, where before they passed every check and failed only when the container started. CI also boots the production server (`scripts/smoke-boot.sh`: `node src/db/migrate.ts && node server.prod.ts`, the container's command, against a throwaway Postgres with dummy but valid environment) and polls `/api/health`, then sends SIGTERM and requires the server to exit with code 0 within 15 seconds. The boot found that it didn't: srvx closed its listener on SIGTERM but the database pool kept the process alive until Docker's SIGKILL. `server.prod.ts` now does its own orderly shutdown (`src/server/shutdown.ts`, srvx's turned off): stop maintenance, close the listener and the realtime sockets (each disconnect checkpoints its presence interval), end the pool, exit 0, with a hard exit after 8 seconds, inside Docker's 10. The pool lives in a process global so the SSR bundle's and `server.prod.ts`'s copies of `src/db/client.ts` share it and `closeDb` ends it. That step is informational: gating the deploy on CI stays out of scope, by choice. And `src/db/migrate.ts` imports the server's environment validation, so a missing or malformed variable stops the container before migrations run, not after.

## Addendum: searchable logs and a minimal server baseline (2026-10-14)
Decided with the operator (issues #108, #112, #113; built in #119). Server logs used to be `console.*` text in Docker's `json-file` files (3 × 10 MB), deleted whenever a deploy recreated the container, with no way to search them and no record of which commit was running.
- **VictoriaLogs and Vector in the stack.** `app` writes **one JSON object per line to stdout**, through one logger (`src/server/logger.ts`) that replaced every server-side `console.*`. A `vector` service, built from `vector/` (pinned by digest, as `backup/` is), reads the app container through the Docker socket and sends it to a `victorialogs` service, which keeps **90 days** in a local `vlogs` volume and serves its viewer on `${HOST_BIND}:9428`. Basic auth (`LOGS_VIEWER_USER`, `LOGS_VIEWER_PASSWORD`, stack variables) covers the viewer and the inserts; the port is LAN-only like the app's and not on the tunnel. Compose labels the app container so Vector finds it whatever the stack is named.
- **Trade-offs accepted:** Vector reads the Docker socket (root-equivalent on the host); lines written while Vector is down or before it first attaches are lost, so a deploy that recreates it loses a few seconds; VictoriaLogs needs about 512 MiB of headroom (the container is capped at 768 MiB, and a burst under 256 MiB was OOM-killed in testing); the log stack has no healthcheck or alert yet.
- **Not backed up.** The logs are diagnostic. `backup` still dumps Postgres only, and `vlogs` stays off the NAS. Logs hold real user and room ids for 90 days, longer than room data (30 days, ADR 11) and equal to quality samples (ADR 11 addendum), admin-only. They never hold IP addresses, chat content, tokens or session ids; the logger enforces that, and a test guards it. A consequence: the "Ignoring cf-connecting-ip" warning no longer names the peer's address.
- **What is redacted, and where.** Besides fields named like secrets and addresses in text, the logger removes the parameters Drizzle appends to a failed query's message and stack (`params: ...`: session and OAuth tokens), OAuth `code` and `state` values and invite tokens, in messages, stacks and `cause` chains. Start prints a failed server function's whole error with `console.error`, so `server.prod.ts` routes `console.*` through the logger (`src/server/console-capture.ts`); Vector additionally drops non-JSON lines that show `params:` and masks credential-like values, as a net. The logger writes to `process.stdout` directly (it ignores a broken pipe, which `console` did) and never through `console`. Each room timeline event the recorder takes is also logged at info as `timeline.<kind>`. `LOGS_VIEWER_USER` and `LOGS_VIEWER_PASSWORD` are required (`${VAR:?}`) so the viewer can't start open, which makes every compose command need them (Dockhand's earlier trouble with `:?` is a risk to watch on the first deploy).
- **Sampling.** The same event from the same user or socket is written in full for its first 10 lines a minute, then as one count line a minute. Errors are counted by message, so a new error is always written.
- **The commit.** Dockhand copies the repo without `.git` and passes no commit, so the image build asks GitHub for `main`'s newest commit (`scripts/fetch-commit.ts`), falls back to `unknown` offline, and bakes it into the image (`COMMIT`). The source changed on 2026-10-14 (#121): the first version used the REST API alone, whose unauthenticated limit is 60 requests an hour per IP, and the homelab's IP shares that with the rest of its network, so the limit was already spent and the first deploy reported `unknown`. The script now reads `refs/heads/main` from git's smart-HTTP advertisement (`https://github.com/theHimanshuShekhar/BhayanakCast.git/info/refs?service=git-upload-pack`: plain HTTPS, no auth, no API quota, parsed from its pkt-lines without `git`), tries the REST API only if that fails, and then writes `unknown`; each request has a 10 s timeout and nothing here can fail the build. It is exact unless a push lands between Dockhand's clone and the build, and Docker's layer cache can keep a previous commit's number across a commit that changes none of the app's files. Every log line carries it, and `/api/health` returns `{ok, commit, startedAt}`. That endpoint is public, but so is the repo.
- **Crashes.** A boot line records commit, boot time and Node version; a shutdown line records the reason. An `unhandledRejection` is logged at error and the server keeps running, so one bad promise doesn't drop every room. An `uncaughtException` is logged, then the server shuts down through the same orderly path as SIGTERM (`src/server/shutdown.ts`) and exits 1, and `restart: unless-stopped` brings it back.
- **Later, by choice:** client crash reporting, uptime monitoring and alerts, and health checks for the log stack itself.
