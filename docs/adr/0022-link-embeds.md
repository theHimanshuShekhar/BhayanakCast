# 22. Link embeds and generated share images

Date: 2026-10-03 · Status: accepted

## Decision
Pasting a link into Discord, X, Slack, WhatsApp, Telegram, Facebook or LinkedIn unfurls as a card. Every page carries Open Graph and Twitter tags, a description and a `theme-color` (the accent, which Discord paints as the embed's bar), built by pure functions in `src/lib/embed.ts` and set from each route's `head()`. Crawlers run no JS, so the tags are in the server-rendered HTML.

- **Origin.** Every absolute URL (`og:url`, `og:image`) is built on `BETTER_AUTH_URL`, read by a server function (`src/lib/embed.functions.ts`) in the root route's `beforeLoad` and passed to every `head()` as `match.context.origin`. Nothing hardcodes the host.
- **Per page.** The root sets the site's tags as the default and routes override them by name (TanStack Router keeps the deepest tag for a `name` or `property`).
  - `/`: the site card, with the 1200x630 `public/og-image.png`.
  - A public live room: its name as the title, "Live now · hosted by <host> · <n> watching · join on BhayanakCast" as the description, and its own card image `/api/og/room/<id>.png?v=<newest thumbnail ms>` (the `v` only changes the URL when the picture does, so Discord's cache lets go).
  - `/past/<id>` and `/profile/<id>`: a title and a description from the recap or profile, with the site image.
  - A private room, an invite link, or a room link a visitor can't see: generic tags and the site image (below).
- **The redirect.** `/room/<id>` sends visitors to `/?join=<id>` in `beforeLoad`, and every crawler is a visitor, so crawlers read the home route. Rather than render the room route for visitors (a bigger change to a page built around a signed-in session), the home route's loader already fetches the room for `?join=` as the visitor, and its `head()` emits the room's tags from that. The room's `og:url` is `/?join=<id>`, the URL that answers 200 with these tags: naming `/room/<id>` would make it and its redirect target each other's canonical, which Facebook and LinkedIn (they follow `og:url`) would loop on. Someone signed in who opens `/?join=<id>` is sent on to `/room/<id>` by the home route's `beforeLoad`. No access rule changed: the room is read through `getLiveRoom` as a visitor, and the room route's guard is as it was. Only the home page, a room, a recap, a profile and the "isn't available" card set `og:url`; the root's default has none.
- **Images.** `satori` lays a tree out as SVG and `@resvg/resvg-js` rasterises it (`src/server/og-card.ts`). The prebuilt `linux-x64-musl` and `arm64-musl` binaries are in the lockfile, so the `node:26-alpine` image resolves one; both packages sit in `dependencies`, which Vite leaves external, so the runtime image's `node_modules` supplies them. The font is JetBrains Mono from `@fontsource/jetbrains-mono`, in its `.woff` files (satori reads TTF, OTF and WOFF but not the WOFF2 the CSS uses), in four Unicode ranges, so Latin, Cyrillic and Greek names draw; anything else is dropped from the text rather than drawn as a box. A render is about 150 ms; the first, cold one (loading fonts and compiling the WASM) took 901 ms in the production container. The route imports the pipeline lazily, inside its handler, so satori, resvg and libwebp stay out of every page's server bundle and a native library that won't load breaks only the cards.
- **The site image** is `public/og-image.png`, drawn by `pnpm og:image` (`scripts/og-assets.ts`) with the same renderer and committed, as are `public/apple-touch-icon.png` and `public/favicon.png` (some unfurlers and browsers ignore an SVG icon). Re-run it after changing the design in `og-card.ts`. It follows DESIGN.md: midnight ink, one monospace face, screens in dark wells, red only on the one live screen, no glow.
- **The room card** is `GET /api/og/room/<id>.png` (a file route, no session). It reads the room as a visitor, draws the name, the host's name and Discord picture, a solid LIVE chip, how many are watching and, behind them, the newest thumbnail of whoever is streaming (the striped stand-in when none). A thumbnail is a WebP, which resvg silently draws as nothing, so it is decoded with `@jsquash/webp` (libwebp as WASM, handed the compiled module because Node's `fetch` can't load the package's own `file:` URL) and re-encoded as a PNG data URI; the data URI is internal to the SVG and no concern of the CSP. The host's picture is fetched from Discord's CDN only (the same host check as the UI), as a small PNG, within 2 s and 256 KB, and is initials on any failure.
- **Caching and limits.** Rendered PNGs sit in an in-memory LRU of 32, keyed by room id, newest thumbnail time, viewer count, room name and host. The viewer count is exact, not bucketed, because it is printed on the card, and a room holds at most ten people, so it is a bucket in effect. The cache holds promises, so unfurls arriving together share one render. The response is `image/png` with `Cache-Control: public, max-age=60`: it is the same for everyone, so `withPrivateCaching` leaves it alone (it only forces `private, no-store` on HTML, server functions and `/api/auth`, and on responses with no cache header). The route is limited per client IP like the other public reads (ADR 20 addendum), as a new `card` kind of 30 a minute. It is checked before the cache, and a client over its budget gets the same 302 to the site image as any other no-card case, not a 429: that answer is cheap, names nothing, and several Discord crawlers can share an egress IP, so a 429 would cost them the image on what are mostly cache hits.
- **Privacy.** A private, ended or unknown room can't be told apart, and the image route answers all three with a 302 to `/og-image.png` (a render error does the same, so an embed never shows a broken image). The page tags for them are the same generic ones: "This room isn't available". An invite link (`/join/<token>`) gets "A private room on BhayanakCast" whether or not the token is valid, with no `og:url` at all (not even the site root, so Facebook and LinkedIn keep the link they were given) and no image URL that names the room or token; the token is in the page's URL only. The public room builder also refuses a room marked private, so a mistake in a caller can't put a private name in a tag. The card route never reads a thumbnail or the host's picture for a room it won't draw.

## Consequences
- A pasted public room link shows the room's name, host, viewers and screen; a private one shows nothing about the room. The invite page's loader data (in the body, not the head) still holds the room name for whoever has the link, as it did.
- Drawing a card costs CPU on the app's event loop (about 150 ms warm, 901 ms cold), bounded by the cache, the per-IP limit and the 32-entry LRU. A busy site would move it to a worker.
- Two more dependencies of note: `@jsquash/webp` (about 900 KB, only to decode thumbnails) and the font package. A future resvg that reads WebP would remove the first.
- Cloudflare's Bot Fight Mode could challenge the crawlers; docs/deploy.md says how to check.
